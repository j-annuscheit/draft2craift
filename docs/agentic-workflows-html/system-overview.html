Step 1

Runtime Model in One Picture

User Request
  -> AgenticWorkflowService.run_*()
    -> load definition + profile + overlays
      -> engine: execute step graph
        -> runner(ctx, step, projected)
          -> tools.call(...)
        -> StepOutcome (value/updates/jump/candidates)
        -> engine commits or discards staged candidates
        -> edge conditions + max_visits decide next step
      -> terminal step writes result
  -> UI gets markdown + meta

The crucial point: The workflow definition controls the flow, not the runner alone. Runners are functional building blocks; edges + conditions determine the orchestration.

Definition vs. Profile vs. Runner

definition (TOML)
  • Defines step order and edges.
  • Defines projections (Least Privilege for steps).
  • Defines terminal steps and budgets.
profile (TOML)
  • Defines policies (e.g., max tries, depth, filter).
  • Defines model_routing and wiring overrides.
  • Is interchangeable depending on environment/use case.
The runner remains the same, but its behavior changes via policy values from the profile. For mind maps, the current productive path is the small worker chain with map.*.v1. The graph workflow also uses an older, separately wired path with mindmap.*.v1 runners for the graph logic.

What Data a Step Really Gets

A step does not operate freely in the entire system, but within a small contract. When you later read or write a runner yourself, these are the fields that matter.

SourceContentTypical Questions
ctx.requestOriginal user request and runtime parameters.What did the user want? Which mode is active?
ctx.stateResults of previous steps.What did the previous step already calculate?
ctx.policyConfigurable limits and switches.How many retries? What limits? Which filters?
projectedThe filtered input intended for this step.Which fields should the step officially use?
ctx.toolsAllowed tools like LLM, RAG, Canvas.Which external actions may the step trigger?

Important Contracts (Concrete)

shared/services/agentic/contracts.py
@dataclass(slots=True)
class StepDef:
    id: str
    runner: str
    input_projection: str = ""
    args: dict[str, Any] = field(default_factory=dict)
    write_to: str = ""
    on_error: str = "fail_hard"
    max_visits: int = 0
    on_max_visits: str = ""

@dataclass(slots=True)
class StepOutcome:
    value: Any = None
    updates: dict[str, Any] = field(default_factory=dict)
    jump: str = ""
    stop: bool = False
    meta: dict[str, Any] = field(default_factory=dict)
    candidate_writes: dict[str, dict[str, Any]] = field(default_factory=dict)
    commit_candidates: tuple[str, ...] = ()
    discard_candidates: tuple[str, ...] = ()

@dataclass(slots=True)
class WorkflowRunResult:
    ok: bool
    workflow_id: str
    profile_id: str
    result: dict[str, Any]
    state: dict[str, Any]
    trace: list[StepTrace]
    errors: list[str]
    metrics: dict[str, Any]

@dataclass(slots=True)
class StepTrace:
    step_id: str
    runner: str
    status: str
    duration_ms: float
    reason: str = ""
    visit_index: int = 0
    input: dict[str, Any] = field(default_factory=dict)
    output: dict[str, Any] = field(default_factory=dict)
    state_after: dict[str, Any] = field(default_factory=dict)

StepOutcome is the central return object. Only with it can a runner mutate the state, trigger a retry, or stop cleanly.

In practice, this means: A runner never writes directly to the GUI or global variables. It only returns a StepOutcome, and the engine takes care of the rest.

Also new is that the trace per step now stores not only status and duration, but also the projected input, the direct step result, and the written state after the step. This makes debugging much more concrete.

Three Control Paths per Step

In the current system, a step no longer has just "next edge yes or no," but three levels of control.

  • Normal edge conditions via when = "...".
  • Direct jumps by the runner via StepOutcome.jump.
  • Overflow path via max_visits + on_max_visits if the same step is reached too often.
[[steps]]
id = "select_frontier_node"
runner = "map.select_frontier_node.v1"
input_projection = "select_frontier_node_input_v1"
write_to = "map_frontier"
max_visits = 96
on_max_visits = "detect_coverage_gaps"

In practice, this prevents broken loops. So if a step lands in the same place sixteen times, it doesn't continue silently but is redirected to another step in a controlled manner.

Why Projections Are Important

Ideally, each step only sees the necessary part of the request/state/policy. This reduces coupling and lowers the risk of a runner implicitly relying on other fields. 

[projections.validate_candidate_tree_input_v1]
include = [
  "state._candidates.map_result_candidate",
  "state.map_result.root_label",
  "state.map_request.topic",
  "policy.map_min_nodes",
  "policy.map_max_nodes",
  "policy.map_max_edges",
  "policy.map_max_depth",
  "policy.map_require_single_root",
  "policy.map_allow_cycles",
  "policy.map_max_isolated_nodes",
  "policy.map_require_connected_graph",
  "policy.map_node_min_word_letters"
]
Without projection discipline, workflows become difficult to maintain because runners then expect "global" state.

This also applies to candidate validators. If a validator is to decide between the old and new output, the projection must contain both the current state and the staged candidate.

How to Classify Errors Architecturally

  • If user input is missing in the step, first check the GUI request and service call.
  • If a policy value is missing, check the profile and projection.
  • If a runner is not found, check the export, registry, and wiring.
  • If the output structure is wrong, check the runner logic and edge conditions.
  • If you see no result at all, check the terminal step and the GUI finalization.

Domain Rules in this Tutorial

Only 1 component at the end Nodes must have word labels Mind map duplicates are merged Risky changes are staged as candidates first Loops have visit guards Expansion in controlled rounds UI controls depth via slider

These rules are intentionally strict so that the output for downstream processing (Canvas, graph analysis, QA) remains structurally stable.
