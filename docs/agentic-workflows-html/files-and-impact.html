Step 4

Goal of this step

A workflow is only really usable when it is completely wired from the GUI actions to the service wrapper. This page shows the current actual state for Mindmap v3 and the still existing Graph path.

1) Service Entries: run_mindmap and run_graph

shared/services/agentic/service.py
def run_mindmap(
    self,
    *,
    request: dict[str, Any],
    tools: dict[str, Any] | None = None,
    profile_id: str = "mindmap_grounded_graph",
    enabled: bool | None = None,
    ...
) -> WorkflowRunResult:
    if not _feature_enabled("D2C_AGENTIC_MINDMAP", enabled):
        raise RuntimeError("Agentic mindmap disabled (D2C_AGENTIC_MINDMAP=1 to enable).")
    return self.run(
        workflow_id="mindmap_agentic",
        request=request,
        profile_id=profile_id,
        ...
    )


def run_graph(
    self,
    *,
    request: dict[str, Any],
    tools: dict[str, Any] | None = None,
    profile_id: str = "graph_connected_component",
    enabled: bool | None = None,
    ...
) -> WorkflowRunResult:
    if not _feature_enabled_any(("D2C_AGENTIC_GRAPH", "D2C_AGENTIC_MINDMAP"), enabled):
        raise RuntimeError("Agentic graph disabled (D2C_AGENTIC_GRAPH=1 to enable).")
    req = dict(request or {})
    req["mode"] = "graph"
    return self.run(workflow_id="graph_agentic", request=req, profile_id=profile_id, ...)

The wrappers encapsulate activation, default profile and the actual workflow name. The rest of the app therefore does not need to know which internal TOML file is loaded.

5) Useful final message in the chat

For Mindmap and Graph, the chat finalization today reads real runtime metadata from the run and, depending on the user mode or setting, shows a compact or more detailed summary. 

✅ MindMap created.
20 nodes, 19 connections, depth 6
Focus: Technical risks of the bachelor thesis
Structure: 1 component, 1 root
Run: 6 LLM calls, 19 steps, 12.2 s
This output does not come from a second analysis, but directly from the workflow state and the runtime metrics.

6) Trace for real debugging work

If trace_enabled is active, a JSON file is created under runs/agentic/.... In the v3 path, it is visible per step which projection arrived, which result was written and whether a candidate was currently in play. 

{
  "step_id": "validate_candidate_tree",
  "runner": "map.validate_candidate_tree.v1",
  "status": "ok",
  "visit_index": 7,
  "input": {
    "state._candidates.map_result_candidate": {"meta": {"intent": "attach_children"}},
    "state.map_result.root_label": "Bachelor's thesis",
    "policy.map_node_min_word_letters": 3
  },
  "output": {
    "value": {"ok": true, "reason": "ok"},
    "candidate_writes": {
      "map_result_candidate": {"meta": {"validated": true}}
    },
    "write_to": "map_validation"
  },
  "state_after": {
    "map_validation": {"ok": true, "reason": "ok"},
    "state._candidates.map_result_candidate": {"meta": {"validated": true}}
  }
}

Exactly this view makes it possible to trace whether a problem comes from GUI input, profile, worker or commit logic.

7) Two internal state areas you should know

PathRoleWhy important
state._runtime.step_visits.*Counts how often a step has already been entered.Explains overflow paths and loops.
state._candidates.*Contains staged candidates before the commit.Shows whether a suggestion has already been accepted or is still only under review.

If something doesn't arrive in the GUI

  • First check llm_tasks.py: Is request.query, request.depth and context_text really set?
  • Then check the service wrapper: Is run_mindmap or run_graph started?
  • Then check settings and profile: Is the workflow active and the expected profile selected?
  • If loops seem strange, look in state._runtime.step_visits and in the trace.
  • If the workflow ran but nothing became visible, check map.emit_result.v1 or the graph terminal step.
