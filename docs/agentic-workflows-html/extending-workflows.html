Step 6

Goal

You want to try out new agents/workflows quickly without losing maintainability. That's why you always use the same insertion pattern: Runner -> Registry -> Definition -> Profile -> Service/UI -> Tests.

The shortest safe sequence

  1. First, build the business logic as a runner.
  2. Give the runner a stable name and register it.
  3. Then create the workflow definition that uses this runner.
  4. Then create a profile with conservative defaults.
  5. Only wire the workflow into the GUI/Settings if it should be visible to users.
  6. Finally, write at least one end-to-end test and one negative case.
This order is intentionally chosen this way: each later stage depends on the name and behavior of the earlier stage. If you start with the GUI, you are still missing the stable core.

1) Create a new runner

shared/services/agentic/templates/step_runner_template.py
from shared.services.agentic.contracts import StepOutcome


def runner_template(ctx, step, projected):
    _ = step, projected
    input_value = str(ctx.request.get("example_input", "") or "").strip()
    if not input_value:
        return StepOutcome(
            value={"ok": False, "reason": "empty_input"},
            updates={"state.example_status": "empty_input"},
        )
    transformed = input_value.upper()
    return StepOutcome(
        value={"ok": True, "text": transformed},
        updates={"state.example_status": "ok"},
    )
Rule: Runners must be deterministic enough, not import UI, and only communicate via StepOutcome.

If you are unsure, always start with a very small runner that has only one clear input and one clear output. You can then add extensions like retries, LLM calls or cleanup step by step.

Important for the current system: Everything you return as StepOutcome.value or StepOutcome.updates also automatically ends up in the extended trace. You don't have to write a second debug step for this.

For riskier steps, there is now a second pattern: A runner can only store a candidate in candidate_writes and leave the actual decision to a later validator. 

return StepOutcome(
    value={"retry": True, "reason": "candidate_proposed"},
    candidate_writes={
        "candidate_output": {
            "write_to": "state.work",
            "value": {"items": transformed_items},
            "meta": {
                "intent": "propose",
            },
        }
    },
)

2) Extend registry directly

shared/services/agentic/default_registry.py
from .workers.myflow import extract_entities as myflow_extract_entities

registry.register("myflow.extract_entities.v1", myflow_extract_entities.run)

Without a registry entry, the engine cannot resolve the runner, even if the function exists.

Naming conventions are very useful here. A name like map.propose_child_nodes.v1 already says which area the runner belongs to, what it does and which version is meant.

In the current implementation, there is no additional export layer anymore. New runners are registered directly from their file under shared/services/agentic/workers/ in the default registry module.

3) New workflow definition (flow graph)

schema_version = 1
workflow_id = "myflow_agentic"
workflow_version = "1.0.0"
job_type = "myflow"
entry_step = "step_a"
terminal_steps = ["emit", "fail_hard"]

[state_init]
work = {}

[projections.step_a_input_v1]
include = ["request.query", "policy.some_limit"]

[[steps]]
id = "step_a"
runner = "myflow.my_new_step.v1"
input_projection = "step_a_input_v1"
write_to = "work"
max_visits = 6
on_max_visits = "fail_hard"

[[steps]]
id = "emit"
runner = "control.emit_result.v1"
input_projection = "step_a_input_v1"

[[steps]]
id = "fail_hard"
runner = "control.fail.v1"

[[edges]]
from = "step_a"
to = "emit"
Important: Every runtime step needs an input_projection (except fail_hard). This is ensured by tests/services/test_agentic_definition_projections.py.

If you read a definition without prior knowledge, don't read it as a text file, but like a flowchart: start step, intermediate steps, terminal step, then the conditions on the edges.

max_visits and on_max_visits form the third standard path of a step: success, normal fallback and overflow fallback if there are too many repetitions.

If you are working with candidates, you will almost always need an additional validator step that sees the same technical state plus state._candidates.* and then decides via commit_candidates or discard_candidates.

4) Create profile (Policies + Wiring)

schema_version = 1
profile_id = "myflow_default"
workflow_id = "myflow_agentic"
profile_version = "1.0.0"

[policy]
max_runtime_seconds = 60
max_llm_calls = 6
some_limit = 10

[model_routing]
"myflow.step_a" = "llm.default"

[wiring]
"myflow.step_a" = "myflow.my_new_step.v1"

Separating definition and profile makes experiments easy: test a new policy without touching the flow graph.

Only use keys that the engine or the runner actually evaluate. Unimplemented desired keys do not belong in the profile as a precaution, but only when the corresponding runner or engine path exists.

This is exactly why you should first try out new ideas via profile values. Only when it turns out that an additional step or a different order is necessary, you have to go to the definition itself.

Profiles and definitions are currently available exclusively as .toml. This reduces parser dependencies and makes the loading paths clear.

5) Optional: Service Wrapper + GUI Integration

  • shared/services/agentic/service.py: optional run_myflow(...) analogous to run_graph.
  • shared/services/agentic/settings.py: extend key/id/default profile.
  • shared/config/setting_keys.py: add persistent keys.
  • studio/controllers/agentic_settings_ctrl.py: wire up save/load.
  • studio/agentic/settings_dialog.py: new workflow line + user mode labels.

You only need this part if the workflow should be directly selectable for users or permanently configurable. For internal experiments, Service + Tests are often sufficient.

6) Test matrix (minimum)

# 1) Definitions correct
PYTHONPATH=. pytest -q tests/services/test_agentic_definition_projections.py

# 2) Settings parse + defaults
PYTHONPATH=. pytest -q tests/services/test_agentic_settings.py

# 3) End-to-end workflow behavior
PYTHONPATH=. pytest -q tests/services/test_agentic_workflows.py

# 4) Domain-specific invariants (e.g. map/graph cleanup)
PYTHONPATH=. pytest -q tests/services/test_agentic_mindmap_validation.py

These four test types cover different error classes: structural errors in definitions, wrong defaults, broken end-to-end execution and technical invariants in the domain code.

7) Final checklist

  • New runners are registered and addressable via wiring.
  • Loop steps have explicit max_visits limits.
  • Candidates are only committed or discarded after validation.
  • Workflow has only necessary projections (least privilege).
  • Policy defaults are conservative and explicitly documented.
  • GUI uses user mode label resolution instead of hard strings.
  • Trace can be read immediately in case of errors (runs/agentic/*).
