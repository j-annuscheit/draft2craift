Step 3

What is really configured on this page

This page describes the currently active Mindmap v3 workflow as it is actually wired in the project. There is no v2 path here anymore. The productive mind map runs via mindmap_agentic with the profile mindmap_grounded_graph.

  • Definition: Steps, Edges, Projections, Budgets.
  • Profile: Policies, Model-Routing, Cache, Wiring.
  • Runtime: Commit/Discard of Candidates, Trace, Visit-Guards.
  • GUI: passes query, full context and desired depth to the request.
For Graph, the following currently applies: It still has its own workflow and does not yet use the complete v3 worker chain. Therefore, the mind map examples below deliberately only describe the current Mindmap v3 path.

1) Deliberately separate definition, profile and worker

LayerPathResponsibility
Definitiondata/workflows/definitions/mindmap_agentic.tomlFlow graph, projections, terminal steps, budgets
Profiledata/workflows/profiles/mindmap_grounded_graph.tomlPolicies, wiring and model routing
Workershared/services/agentic/workers/maps/**small technical steps
Runtimeshared/services/agentic/engine.pyStep execution, visit guards, candidate commit, trace

This separation ensures that we can change policies or routing without having to constantly rewrite the technical flow graph.

map_metrics = { frontier_visits = {}, candidate_commits = 0, candidate_discards = 0, expansion_round = 0, gap_round = 0 }

The runtime also creates two additional buckets during the run: state._runtime for technical runtime data and state._candidates for staged candidates.

  • map_result is the currently accepted mind map state.
  • map_candidate is not yet an accepted tree, but only the current suggestion.
  • map_seed_concepts and map_seed_enrichment encapsulate the small initial expansion directly after the seed.
  • map_gaps and map_gap encapsulate the later gap-fill loop.
  • map_metrics shows expansion, gap rounds, commits and discards.
  • state._candidates.map_result_candidate contains the next possible tree before the commit.

4) The actual Mindmap v3 flow graph

The core of the v3 workflow is now four-stage: deterministic seed, small seed extension, controlled frontier loop and then a targeted gap-fill round. 

resolve_request
-> collect_context
-> normalize_context
-> segment_context
-> extract_outline
-> score_focus_sections
-> choose_root_label
-> seed_from_outline
-> extract_seed_concepts
-> propose_seed_enrichment
-> parse_seed_enrichment
-> validate_seed_enrichment
-> commit_initial_tree
-> select_frontier_node
  -> collect_frontier_evidence
  -> extract_local_candidates
  -> propose_child_nodes
  -> parse_child_nodes
  -> repair_child_nodes (only for format errors)
  -> validate_child_nodes
  -> attach_child_nodes
  -> validate_candidate_tree
  -> commit_candidate_tree
  -> update_coverage
  -> decide_continue_expansion
  -> select_frontier_node (Loop)
-> detect_coverage_gaps
  -> select_gap_target
  -> propose_gap_fill
  -> parse_gap_fill
  -> validate_gap_fill
  -> attach_gap_fill
  -> validate_candidate_tree
  -> commit_candidate_tree
  -> update_coverage
  -> detect_coverage_gaps (Loop)
-> normalize_labels
-> merge_semantic_duplicates
-> ensure_single_root
-> ensure_connected_tree
-> validate_final_tree
-> render_markdown
-> emit_result

This is the biggest difference to the older paths: The workflow no longer repeatedly rewrites a complete map, but only extends a part in a controlled manner.

5) Real step definitions with visit guards

data/workflows/definitions/mindmap_agentic.toml
[[steps]]
id = "select_frontier_node"
runner = "map.select_frontier_node.v1"
input_projection = "select_frontier_node_input_v1"
write_to = "map_frontier"
on_error = "continue_with_defaults"
max_visits = 96
on_max_visits = "detect_coverage_gaps"

[[steps]]
id = "propose_child_nodes"
runner = "map.propose_child_nodes.v1"
input_projection = "propose_child_nodes_input_v1"
write_to = "map_candidate"
on_error = "continue_with_defaults"
max_visits = 48
on_max_visits = "decide_continue_expansion"

[[steps]]
id = "select_gap_target"
runner = "map.select_gap_target.v1"
input_projection = "select_gap_target_input_v1"
write_to = "map_gap"
on_error = "continue_with_defaults"
max_visits = 32
on_max_visits = "normalize_labels"

Each loop step thus has three possible paths: continue normally, branch differently via an edge condition or run hard via on_max_visits into a safe end path.

6) Candidate pattern: attach - validate - commit/discard

In v3, risky state changes always run via a staged candidate. Only then is the new tree normalized, validated and accepted or discarded. 

# attach_child_nodes / attach_gap_fill
accepted nodes become state._candidates.map_result_candidate

# validate_candidate_tree
the candidate is normalized and checked again

# commit_candidate_tree
on ok:   commit_candidates=("map_result_candidate",)
on fail: discard_candidates=("map_result_candidate",)
This is the central robustness gain. Bad LLM answers can no longer silently destroy a good accepted state.

If you write a worker and it never runs, it's almost always a wiring problem: definition, profile and registry must all speak the same name.

9) GUI/User-Mode: Depth is overwritten at runtime

The GUI passes the desired depth as request.depth. In the Mindmap v3 path, this currently becomes the upper limit for map_max_expansion_rounds. In the graph path , on the other hand, the older switches map_expand_enabled and map_expand_target_depth remain active.

This is precisely why this logic does not belong in the profile alone. The user mode and the chat dock build the runtime request into the request and policy overrides.

10) Typical errors when rebuilding

  • Created a new policy key, but forgot it in the projection.
  • Registered a worker, but forgot the wiring entry in the profile.
  • Wrote candidates directly to state.map_result instead of staging.
  • Forgot max_visits on loop steps.
  • Mixed up Mindmap v3 and Graph legacy in the docs or wiring.
  • Tested GUI depth, but didn't check the runtime path in llm_tasks.py.
