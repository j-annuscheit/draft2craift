Step 2

What a Worker is in the Current Mindmap-v3 Path

The productive mind map workflow no longer builds the map in one large draft step. Instead, there are many small workers with clear responsibilities. This is the core idea from mindmap-worker-architektur-v3.md and this is exactly how it is now implemented in the code.

Important: This step describes the active mind map path. The graph workflow currently still uses an older, separately wired set of workers. This is intentionally not the same as the new mindmap-v3 path.

The Worker Families

AreaPathTask
Sourceworkers/maps/source/Normalize request, adopt context, clean up, segment, extract outline
Seedworkers/maps/seed/Generate deterministic start tree and prepare small initial additions
Frontierworkers/maps/frontier/Select next expansion point, gather evidence, fix format, detect gaps and fill them specifically
Validateworkers/maps/validate/Check candidates and the entire tree
Applyworkers/maps/apply/Attach candidates, commit, update coverage, final cleanup
Renderworkers/maps/render/Render and emit final Markdown

This division is the real maintainability gain. If a problem lies in prompting, in deduplication, or in commit behavior, you only work on a small part.

1) Request Worker: start small and deterministic

shared/services/agentic/workers/maps/source/resolve_request.py
WORKER_ID = "map.resolve_request.v1"


def run(ctx, step, projected):
    _ = ctx, step
    query = str(projection_get(projected, "request.query", "") or "").strip()
    depth = projection_get(projected, "request.depth", 0)
    try:
        target_depth = int(depth or 0)
    except Exception:
        target_depth = 0
    target_depth = max(2, min(10, target_depth or 4))
    topic = query or "Mindmap from context"
    return StepOutcome(
        value={
            "topic": topic,
            "focus": query or topic,
            "mode": "mindmap",
            "target_depth": target_depth,
            "style_constraints": [],
        },
        meta={"query_chars": len(query)},
    )

This worker intentionally does very little: it normalizes the user request and derives a stable target depth. It knows nothing about parsing, LLMs, or the rest of the map.

2) Seed Worker: deterministic first, LLM only for small initial additions

shared/services/agentic/workers/maps/seed/seed_from_outline.py
WORKER_ID = "map.seed_from_outline.v1"


def run(ctx, step, projected):
    _ = ctx, step
    root_label = str(projection_get(projected, "state.map_seed.root_label", "") or "Mindmap")
    outline = dict(projection_get(projected, "state.map_outline", {}) or {})
    focus = dict(projection_get(projected, "state.map_focus", {}) or {})
    spec = build_seed_spec(root_label=root_label, outline=outline, focus=focus)
    markdown = render_markdown(spec)
    stats = spec_stats(spec)
    value = {
        "markdown": markdown,
        "mode": "mindmap",
        "root_label": root_label,
        "version": 1,
        "stats": stats,
        "reason": "seed_from_outline",
    }
    return StepOutcome(value=value, meta={"nodes": int(stats.get("nodes", 0) or 0), "edges": int(stats.get("edges", 0) or 0)})

This is one of the most important differences from the old paths: the first accepted map comes deterministically from the document structure and not directly from an LLM draft.

Immediately after this, in the active path, follow map.extract_seed_concepts.v1, map.propose_seed_enrichment.v1, map.parse_seed_enrichment.v1, map.validate_seed_enrichment.v1 and map.commit_initial_tree.v1. So the first accepted map is: a deterministic seed plus a few validated top-level additions.

3) LLM Worker: only local children for one parent

shared/services/agentic/workers/maps/frontier/propose_child_nodes.py
WORKER_ID = "map.propose_child_nodes.v1"


def run(ctx, step, projected):
    frontier = dict(projection_get(projected, "state.map_frontier", {}) or {})
    evidence = dict(projection_get(projected, "state.map_evidence", {}) or {})
    hints = dict(projection_get(projected, "state.map_candidate_hints", {}) or {})
    query = str(projection_get(projected, "state.map_request.focus", "") or "")
    markdown = str(projection_get(projected, "state.map_result.markdown", "") or "")
    source_text = str(projection_get(projected, "state.map_source.normalized_text", "") or "")
    child_limit = max(1, min(6, int(projection_get(projected, "policy.map_llm_child_limit", 4) or 4)))
    parent_label = str(frontier.get("label", "") or "").strip()
    snippets = list(evidence.get("snippets", []) or [])[:5]
    candidate_terms = [str(item.get("label", "") or "").strip() for item in list(hints.get("candidate_terms", []) or []) if str(item.get("label", "") or "").strip()]
    prompt = (
        "You are expanding an existing mind map.\n"
        "IMPORTANT:\n"
        "- Only generate DIRECT children for exactly ONE existing parent.\n"
        "- No new overall mind map.\n"
        "- No explanations outside of the JSON.\n"
        "- Only use terms that are supported by the evidence or the overall context.\n"
        f"- A maximum of {child_limit} children.\n\n"
        f"Focus: {query}\n"
        f"Parent: {parent_label}\n"
        f"Hints: {', '.join(candidate_terms[:8])}\n\n"
        "Current mind map:\n"
        f"{markdown}\n\n"
        "Local evidence:\n"
        + "\n\n".join(f"[{idx + 1}] {snippet}" for idx, snippet in enumerate(snippets))
        + "\n\nOverall context:\n"
        + source_text
        + "\n\n"
        "Answer ONLY as JSON in this format:\n"
        '{"children":[{"label":"...","evidence_segment_ids":[]}]}\n'
    )
    raw_text = str(ctx.tools.call("llm.generate", prompt=prompt) or "")
    reason = "ok" if str(raw_text or "").strip() else "empty_response"
    return StepOutcome(value={"raw_text": raw_text, "reason": reason, "intent": "expansion"}, meta={"prompt_chars": len(prompt), "snippet_count": len(snippets), "context_chars": len(source_text)})

This worker is only allowed to solve a very small semantic task. It does not generate the entire map, but only direct children for exactly one existing parent.

    ...
    value = validate_child_candidates(
        children=children,
        parent_label=str(frontier.get("label", "") or ""),

A typical v3 principle becomes visible here: first, the LLM is allowed to propose, then deterministic business logic decides what is actually accepted.

If the raw response only has a format problem, map.repair_child_nodes.v1 now runs beforehand. This worker tries to save the response with deterministic heuristics instead of immediately forcing another LLM call.

5) Apply Worker: stage candidate instead of overwriting directly

shared/services/agentic/workers/maps/apply/attach_child_nodes.py
WORKER_ID = "map.attach_child_nodes.v1"


def run(ctx, step, projected):
    markdown = str(projection_get(projected, "state.map_result.markdown", "") or "")
    parent_id = str(projection_get(projected, "state.map_frontier.node_id", "") or "")
    accepted_children = list(projection_get(projected, "state.map_validation.accepted_children", []) or [])
    ...
    candidate_spec = attach_children_to_parent(spec, parent_id=parent_id, children=accepted_children)
    candidate_markdown = render_markdown(candidate_spec)
    staged_value = {
        "markdown": candidate_markdown,
        "mode": "mindmap",
        "root_label": root_label,
        "reason": "attached_children",
    }
    return StepOutcome(
        value={"attached_count": len(accepted_children), "reason": "candidate_staged"},
        candidate_writes={"map_result_candidate": {"write_to": "state.map_result", "value": staged_value}},
        meta={"attached_count": len(accepted_children)},
    )

The accepted state remains untouched. The worker only stages a new candidate. The same pattern also applies to map.attach_gap_fill.v1 if a discovered gap is later specifically expanded under an anchor node.

    candidate = dict(projection_get(projected, "state._candidates.map_result_candidate", {}) or {})
    ...
    if bool(validation.get("ok", False)):
        return StepOutcome(
            value={"committed": True, "reason": "candidate_valid"},
            updates={"state.map_metrics.candidate_commits": committed_count + 1},
            commit_candidates=("map_result_candidate",),
            meta={"committed": True},
        )
    return StepOutcome(
        value={"committed": False, "reason": ...},
        updates={"state.map_metrics.candidate_discards": discarded_count + 1},
        discard_candidates=("map_result_candidate",),
        meta={"committed": False},
    )

This is exactly where the candidate pattern from the architecture really comes into play: propose, validate, commit, or discard. No single worker is allowed to silently overwrite the accepted tree. After the frontier loop, map.detect_coverage_gaps.v1 -> map.select_gap_target.v1 -> map.propose_gap_fill.v1 also follows, so that missing document parts are not silently lost.

This is the current style in the project. No runners_*.py collection layer, no hidden export stage, no indirect magic path.

File Order for This Step

  • First create shared business logic under shared/services/agentic/lib/maps/.
  • Then write exactly one worker per file under shared/services/agentic/workers/maps/.
  • Register the worker immediately in shared/services/agentic/default_registry.py.
  • Only then wire the definition and profile to these worker IDs.
